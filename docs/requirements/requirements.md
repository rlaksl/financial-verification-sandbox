# 요구사항·업무 정책

기준일: 2026-11-26

## 0. 문서 기준

- 식별자는 변경하거나 재사용하지 않는다. 문구가 바뀐 요구사항은 비고에 변경 이력(RH-xx)을 표시한다.
- 이 문서는 수치(인증코드 자릿수, 유효기간, 실패 횟수, 결과 사용 기한, 요청 제한 수치, 보관 기간 등)를 정하지 않는다.
- **모든 요구사항은 아직 실행으로 검증되지 않았다.**
- 구현 방식이 PoC 결과에 따라 달라지는 요구사항은 6절에 모았다.

## 1. 기능 요구사항 (확정)

### 1.1 고객사 인증·인가

| ID | 요구사항 | 비고 |
| --- | --- | --- |
| FR-AUTH-01 | 고객사 서버는 자신의 자격 증명으로 Access Token을 발급받는다 | 자격 증명의 형태는 U-01 |
| FR-AUTH-02 | 자격 증명이 틀리면 발급을 거부하고, 어느 값이 틀렸는지 구분해 알려 주지 않는다 | |
| FR-AUTH-03 | Access Token은 짧은 유효기간을 가지며 Refresh Token은 발급하지 않는다 | 수명 값은 상세 설계 |
| FR-AUTH-04 | 토큰에는 고객사에 허용된 Scope 범위 안에서만 권한이 부여된다 | |
| FR-AUTH-05 | 보호 API는 유효한 토큰이 없으면 401로 거부한다 | |
| FR-AUTH-06 | 보호 API는 필요한 Scope가 없으면 403으로 거부한다 | |
| FR-AUTH-07 | 비활성화된 고객사는 토큰을 발급받을 수 없고, 비활성화가 확정된 이후 새로 인가 판단을 받는 요청부터 기존 토큰도 거부된다. 실행 중인 요청의 강제 중단은 요구하지 않는다 | TLS 연결 수명과 별개로 충족한다 |
| FR-AUTH-08 | 고객사를 재활성화해도 비활성화 이전에 발급된 토큰은 다시 유효해지지 않는다 | |
| FR-AUTH-09 | 보호 API는 검증된 토큰의 인증 정보로만 고객사를 식별하고, 요청 본문이나 헤더의 고객사 식별자를 신뢰하지 않는다 | |
| FR-AUTH-10 | 고객사 등록, 상태 변경, 자격 증명 교체는 운영 절차로 수행한다. 관리 API와 관리 화면은 제공하지 않는다 | RH-02 |
| FR-AUTH-11 | 고객사는 자신이 만든 리소스에만 접근하며, 다른 고객사의 리소스는 존재하지 않는 것처럼 응답한다 | 검증은 v0.3부터 |
| FR-AUTH-12 | 자격 증명을 교체하면 이전 자격 증명으로는 토큰을 발급받을 수 없다. 공개키 기반 인증의 정상 회전에서는 FR-AUTH-16의 겹침 기간이 예외다 | RH-02 |
| FR-AUTH-13 | 재활성화는 자격 증명 교체가 완료된 경우에만 성립하며, 교체에 실패하면 비활성 상태를 유지한다 | RH-02 |
| FR-AUTH-14 | 발신자 제한 Access Token만 발급하고, 보호 API는 바인딩 정보가 없거나 바인딩이 일치하지 않는 토큰을 거부한다 | RH-03. 바인딩 방식은 U-01 |
| FR-AUTH-15 | 고객사 인증 자격 증명이나 토큰 바인딩 키·인증서를 긴급 폐기하면 즉시 거부하고, 그에 연결된 토큰도 함께 폐기한다 | RH-03 |
| FR-AUTH-16 | 공개키 기반 인증에서는 정상 회전을 위해 제한된 기간 동안 복수의 키를 허용한다. 겹침 기간은 정상 회전에만 적용하며 재활성화(FR-AUTH-13)와 긴급 폐기(FR-AUTH-15)에는 적용하지 않는다. 침해된 키를 계속 허용하는 것은 이에 해당하지 않는다 | RH-03. 개수·기간은 U-15 |
| FR-AUTH-17 | 신뢰를 늘리는 변경(키 추가, Scope·Grant Type 허용, 재활성화)은 애플리케이션과 독립된 승인 근거가 있어야 반영된다. 신뢰를 줄이는 변경(비활성화, 긴급 폐기, 토큰 폐기)은 즉시 반영된다 | RH-03. 구현 방식은 우선 후보 (D-X60) |
| FR-AUTH-18 | 승인 근거를 검증할 수 없는 고객사 등록 정보는 인증·인가 판단에 사용하지 않으며, 해당 고객사의 인증은 실패 처리된다 | RH-03. 최신성 보호 방식은 우선 후보 (D-X61) |
| FR-AUTH-19 | 고객사의 Access Token 발급은 OAuth 2.0 client_credentials Grant로만 제공한다 | RH-06 |
| FR-AUTH-20 | 보호 API는 자신을 대상으로 발급된 Access Token만 수락한다 | RH-06. T-22, SC-C12 |

### 1.4 1원 계좌 인증

| ID | 요구사항 |

| FR-VERIF-02 | 계좌 확인에 실패하면(없음·불일치·비활성화) 사유를 구분하지 않고 요청을 거부한다 |
| FR-VERIF-03 | 요청이 성공하면 인증 요청과 1원 모의 입금 기록이 함께 생성된다. 금액과 입금자명은 서버가 정한다 |

| FR-VERIF-05 | 같은 고객사·회원·계좌·목적으로 진행 중인 인증은 최대 1건이다 |
| FR-VERIF-06 | 코드가 일치하면 인증 성공 상태가 된다. 불일치하면 실패 횟수가 늘고, 최대 횟수에 도달하면 잠긴다. 만료된 인증은 검증할 수 없다 |
| FR-VERIF-07 | 고객사는 자신이 만든 인증의 현재 상태를 조회할 수 있고, 조회 결과에는 만료 여부가 반영된다 |

### 1.5 결과 사용

| ID | 요구사항 | 비고 |
| --- | --- | --- |
| FR-USE-01 | 인증 성공 결과는 요청 당시와 같은 고객사·회원·계좌·목적으로, 사용 기한 안에서만 사용할 수 있다 | |
| FR-USE-02 | 인증 결과는 업무 요청 1건에만 사용된다. 새로운 결과 사용과 이미 성공한 동일 업무의 재시도를 구분한다. 같은 operationId이고 회원·계좌·목적이 모두 같은 요청만 동일 업무의 재시도로 보고 기존 결과를 반환한다. operationId가 같아도 업무 컨텍스트가 다르면 거부하며, 다른 operationId의 사용도 거부한다. 이미 사용된 인증 결과는 결과 사용 기한이 지나거나 멱등성 기록이 삭제돼도 다시 사용할 수 없다 | RH-08. 응답 유실 후 기존 업무 결과를 복구할 수 있는 기간은 정책 8·9·11에서 정한다 |
| FR-USE-03 | 코드 유효기간과 결과 사용 기한은 별도로 관리한다 | |

| FR-IDEM-07 | 보관 기간 안에서는 같은 키의 재시도로 최초 처리 결과를 복구할 수 있다. 이 재응답은 최초 처리 시점의 결과이고, 인증의 현재 상태는 상태 조회로 확인한다 |

### 1.8 요청 제한

적용 시점은 8절을 따른다. 알고리즘과 수치는 정하지 않았다.

| ID | 요구사항 |
| --- | --- |
| FR-LIMIT-01 | 계좌 인증 요청에는 고객사·회원 기준과 고객사·계좌 기준으로 재요청 간격과 기간별 횟수 제한을 적용한다 |
| FR-LIMIT-02 | 예금주 일치 확인에는 기간별 횟수 제한을 적용한다 |
| FR-LIMIT-03 | 새로운 업무 요청과 계좌 확인 실패는 업무 요청 제한에 집계한다 |
| FR-LIMIT-04 | 같은 멱등성 키의 재시도는 업무 요청 횟수와 인증 실패 횟수를 다시 늘리지 않는다 |
| FR-LIMIT-05 | 고객사 단위로 API 호출량을 제한한다. 멱등성 재요청도 호출량에는 포함한다 |
| FR-LIMIT-06 | 토큰 발급 과정의 반복적인 고객사 인증 시도를 제한하며, 인증 완료 전과 후의 제한 정책을 구분한다 |
| FR-LIMIT-07 | 모든 차단은 고객사별로 독립 적용한다. 고객사 간 합산 횟수만으로 자동 차단하지 않는다 |
| FR-LIMIT-08 | 제한을 초과한 요청은 거부하고 업무 데이터를 변경하지 않는다 |
| FR-LIMIT-09 | 동시 요청에서도 허용 한도를 넘는 요청이 처리되지 않는다 |
| FR-LIMIT-10 | 잠기거나 만료된 인증 뒤의 새 인증 요청은 허용하되 FR-LIMIT-01을 적용한다 |
| FR-LIMIT-11 | 테스트 사용자 로그인의 반복 실패를 제한한다 |

FR-LIMIT-06과 FR-LIMIT-11의 기록 기준은 남의 식별자로 일부러 실패해 정상 사용자를 잠그는 문제를 고려해 상세 설계에서 정한다.

### 1.9 감사 기록

필수 감사 기록은 해당 기능을 구현할 때 적용한다. 적용 시점은 8절을 따르며, 체계 통합과 무결성 기술 비교는 v0.4에서 한다.

| ID | 요구사항 | 비고 |
| --- | --- | --- |
| FR-AUDIT-01 | 고객사 인증 성공·실패, 접근 거부, 예금주 일치 확인, 인증 요청, 모의 입금, 코드 검증 실패·성공, 잠금, 결과 사용, 제한 초과, 고객사 활성화·비활성화·자격 증명 교체·긴급 폐기, 테스트 사용자 관련 보안 이벤트(로그인 실패, 반복 실패 제한 발동, 세션 폐기)를 감사 기록으로 남긴다 | RH-02, RH-09 |
| FR-AUDIT-02 | 감사 기록은 누가, 무엇을, 어떤 대상에, 어떤 결과로, 언제 했는지와 요청 추적 식별자를 담는다 | |
| FR-AUDIT-03 | 감사 기록에 토큰, 고객사 자격 증명의 비밀값, 인증코드, 전체 계좌번호, 비밀번호를 남기지 않는다 | RH-02 |
