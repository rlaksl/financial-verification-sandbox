# 작업 절차와 검증

기준일: 2026-11-28

규칙 자체는 [AGENTS.md](../../AGENTS.md)와 각 프로세스 문서에 있다. 이 문서는 그 규칙을 작업 순서와 검사 명령으로 연결한다. 특정 개발 도구의 설정은 두지 않는다 (D-O15, D-O23).

## 1. 작업 유형별 최소 문서

항상 [status.md](../status.md)를 먼저 읽는다. 그다음 작업 유형에 해당하는 문서의 **관련 절만** 읽고, 필요한 항목은 식별자로 찾는다 (예: `grep -n "D-O25" docs/decision-register.md`).

| 작업 유형 | 읽을 문서 (관련 절) |
| --- | --- |
| 설계 문서 수정, 결정 변경 | 결정 대장 해당 절과 10·11절, [documentation.md](documentation.md) |
| PoC 관문 | [PoC 계획](../poc/plan.md)의 해당 관문, 1절, 7절, 관련 T·SPEC·SRC |
| 정식 기능 (Feature) | 요구사항 해당 FR·NFR과 9절, 관련 업무 정책, 위협 모델의 관련 공격자 |
| CI, Hook, 비밀값 검사 | [ci-cd.md](ci-cd.md), [ADR-0001](../adr/0001-secret-scanning-betterleaks.md), 결정 대장 D-O24 ~ D-O28, D-O33 |
| Issue·PR·브랜치·태그 | [git-workflow.md](git-workflow.md), [project-management.md](project-management.md), [release.md](release.md) |
| AI 리뷰 | [ai-review.md](ai-review.md), 결정 대장 D-O12·D-O13 |

## 2. 착수 전 확인

1. Issue의 목적, 완료 기준, 관련 식별자를 확인한다.
2. 관련 식별자의 현재 상태를 결정 대장에서 확인한다. 대체된 항목은 후속 식별자를 따라간다.
3. 필요한 정책·기술이 미결정인지 결정 대장 10절과 요구사항 9절에서 확인한다. 미결정이면 착수하지 않고 결정을 요청한다 (AGENTS.md 3·4절).
4. 브랜치, 작업 트리, 기준 커밋을 확인한다 (`git status`, `git log -1`).
5. Issue, 결정 대장, 요구사항, PoC 계획에 적힌 정책값·기술 버전·수치·기본값을 서로 대조한다. 불일치가 있으면 어느 쪽도 임의로 고치지 않고 착수 전에 보고한다. 확정되지 않은 값은 승인된 PoC 범위와 실험 조건 안에서만 사용하며, 실험 결과를 정식 결정으로 기록하지 않는다 (AGENTS.md 4절).
6. 변경 허용·금지 범위, 완료 기준, 검증 방법, 승인 범위, 중단 조건을 확인하고, 불명확하면 착수 전에 확인한다. 병렬로 실행하는 작업이면 공유 자원(작업 디렉터리, DB·스키마, 포트, 상태 저장소, 임시 파일, 테스트 키, 증거 경로, CPU·메모리)의 충돌 가능성을 확인하고, 다른 작업이나 성능 측정·테스트 결정성에 영향을 주는 자원은 격리한다. 구체적인 구성은 U-27·U-07a 결정 이후 PoC 계획에서 정한다.

## 3. 작업 전후 검사

| 시점 | 검사 | 명령 | 통과 조건 |
| --- | --- | --- | --- |
| 문서 변경 후 | 필수 파일, 식별자 중복 정의, 상대 링크, 공개 금지 정보 | `python3 -B -I scripts/check-docs.py` | 종료 코드 0 |
| 검사 스크립트 변경 후 | 검사 스크립트 테스트 | `python3 -B -I scripts/tests/test_check_docs.py` | 종료 코드 0 |
| 커밋 전·Push 전 | 비밀값 검사 | 커밋 전 `scripts/secret-scan.sh staged`와 `history`, Push 전 `history`와 전송 대상 커밋(`--rev`). Hook 설치 시 자동 실행되고, Hook이 실행되지 않으면 수동 실행이 필수다. 검사 스크립트가 없는 브랜치는 검증된 실행 파일로 직접 검사 ([ci-cd.md](ci-cd.md) 3절) | 종료 코드 0 |
| 검사 스크립트 변경 후 | 비밀값 검사·설치 스크립트 테스트 | `bash scripts/tests/test_secret_scan.sh`, `bash scripts/tests/test_install_betterleaks.sh` | 종료 코드 0 |
| 커밋 후 | 작성자 정보와 메시지 | `git log -1 --format='%an %cn%n%B%n%(trailers)'` | 기존 작성자 정보, D-O31 위반 표시 없음 |

- 0이 아닌 종료 코드는 모두 실패다. 실패를 우회하지 않는다.
- 검사 결과는 파이프라인 끝의 명령이 아니라 검사 명령 자체의 종료 코드로 판단한다.
- 검증 절차나 검사 스크립트 자체의 오류도 실패로 처리한다. 원인을 확인하기 전에는 통과로 기록하지 않는다.

**검증 증거 재사용.** 커밋 전 staged 변경분 검사와 기존 Git 이력 검사, Push 전 전체 Git 이력 검사, CI 필수 검사는 매번 실행하며 이전 결과로 대체하지 않는다 (D-O25, D-O26). 그 밖의 검사는 다음을 모두 확인할 수 있을 때만 이전 실행 증거를 재사용할 수 있다. 트리 해시나 diff 해시는 확인 수단의 하나일 뿐이며, 그것만으로 같다고 판단하지 않는다. 확인이 어렵거나 하나라도 다르면 다시 실행한다. 모든 검사에 별도의 증거 관리 절차를 요구하지는 않는다.

| 확인 항목 | 내용 |
| --- | --- |
| 검사 대상 | 실제 내용이 같다. 미추적 파일이 결과에 영향을 주면 그 포함 여부도 같다 |
| 의존성 | 검사 대상이 의존하는 파일·패키지가 같다 |
| 도구와 설정 | 검사 스크립트, 테스트 코드, 설정 파일의 내용과 도구 버전이 같다 |
| 실행 환경과 외부 상태 | 운영체제, 런타임, 명령과 옵션, 그리고 결과에 영향을 주는 외부 상태(원격 저장소, 네트워크 응답 등)가 같다 |
| 판정 기준 | 통과 조건과 관련 결정·요구사항·정의 규칙이 바뀌지 않았다 |
| 이전 결과 | 종료 코드 0이고, 필수 검증 항목을 건너뛰거나 누락하지 않고 실제로 수행했으며, 명령·환경·결과가 기록돼 있다 |

`check-docs.py`가 식별자 **정의**로 보는 것은 첫 헤더 칸이 `ID` 또는 `SC`인 표의 첫 칸이다. 다른 표나 본문에서 식별자를 참조하는 것은 중복이 아니다.

- 정의 위치: 아래 접두어의 식별자는 지정 문서의 `ID`·`SC` 표에서만 정의한다. 다른 문서의 `ID`·`SC` 표에서 정의하면 위반이다. 목록에 없는 접두어는 중복 정의만 검사한다.

  | 접두어 | 문서 |
  | --- | --- |
  | D, U, H | decision-register.md |
  | FR, NFR, RH | requirements/requirements.md |
  | SC, FM | poc/plan.md |
  | T | research/technical-issues.md |
  | SPEC, SRC | research/spec-source-analysis.md |
  | C | research/technology-comparison.md |
  | A, B, S, POL, TA, TB, TH | security/threat-model.md |

- 한계: 첫 헤더 칸이 `ID`·`SC`가 아닌 표, 제목, 목록에 쓴 정의는 정의로 인식하지 않는다. 참조 표와 구분할 수 없으므로 이런 정의의 중복과 위치 위반은 탐지하지 않는다. 새 정의는 `ID`·`SC` 표로 작성한다.
- 펜스 코드 블록: 줄 앞 공백 3칸 이하의 백틱·물결표 3개 이상으로 연 블록은 식별자·링크 검사에서 제외하고 공개 금지 검사에는 포함한다. 닫는 펜스는 같은 문자, 같은 길이 이상, 뒤에 공백만 허용한다. 닫히지 않은 펜스는 위반이다. 인용문·목록 안의 펜스, 탭 들여쓰기, 들여쓰기 코드 블록은 인식하지 않는다.
- git 모드(기본)는 추적 파일만 검사한다. 확장자와 관계없이 모든 추적 경로가 git 인덱스(mode 100644·100755)와 작업 트리에서 일반 파일이어야 한다. 작업 트리에 없거나 디렉터리·심볼릭 링크(인덱스 mode 120000 포함) 등이면 위반이다. 미추적 텍스트 파일은 경고(검사하지 않음)다. 필수 파일은 루트 안의 경로인지, 존재하는지, 추적 중인지 확인한다.
- `check-docs.py`는 인덱스가 아니라 **작업 트리의 파일 내용**을 검사한다. 커밋 전에는 stage한 뒤 `git diff --name-only`의 출력이 비어 있는지(인덱스와 작업 트리의 내용 일치) 확인하고, 그 상태에서 문서 검사와 staged 비밀값 검사를 실행한다. 출력이 있으면 검사 결과가 커밋 내용을 대표하지 않으므로 커밋하지 않는다.
- 출력 가림: 공개 금지 위반은 규칙 이름만 출력한다. 파일 경로, `--require` 값, 식별자, 링크 대상은 절대 경로·루트 밖·공개 금지 패턴과 일치하면 `<redacted>`로 출력한다. 패턴 기반이므로 패턴에 맞지 않는 값은 그대로 출력된다. 인자·git·읽기 오류와 예상하지 못한 예외는 오류 종류, 종료 코드, 예외 유형만 출력한다.
- 링크 앵커(`#제목`)와 참조식 링크(`[x]: 경로`)는 검사하지 않는다 (미검증, 후속 작업).

## 4. 실행 증거와 미검증 기록

PR의 검증 절과 PoC 결과에는 다음을 남긴다.

| 항목 | 기록 |
| --- | --- |
| 실행한 검사 | 명령, 실행 환경, 종료 코드, 결과 요약 |
| 실행하지 않은 검사 | "미실행"과 사유. 통과로 세지 않는다 |
| 판정 | PoC는 [plan.md](../poc/plan.md) 7절, 그 외는 [documentation.md](documentation.md) 2절의 검증 상태 값 |
| 근거 유형 | 판단, 명세 확인, 소스 확인, 실행 검증을 구분한다 |
| 재사용한 증거 | 원래 실행 시점, 증거 위치, 동일성을 확인한 항목 |
| 가정과 확인 필요 사항 | 적용한 가정과 근거, 불확실성, 저장소 소유자의 확인이 필요한 항목 |
| 후속 영향 | 다른 Issue, 결정, 문서에 미치는 영향 |

GitHub 템플릿, Actions, Rulesets처럼 외부 플랫폼이 해석하는 설정은 로컬 문법·구조 검사 결과와 플랫폼의 실제 적용·동작 검증 결과를 구분해 기록한다. 로컬 검사 통과만으로 플랫폼 동작이 검증됐다고 판정하지 않으며, 플랫폼에서 실제 적용과 동작(표시, 실행, 차단)을 확인한 경우에만 실행 검증으로 기록한다 (D-O07).

## 5. 작업 종료와 인수인계

- 공개 상태는 PR과 [status.md](../status.md)에 남긴다. status.md 갱신 시점은 [documentation.md](documentation.md) 4절을 따른다.
- 다음 작업자에게 넘길 내용(진행 중 브랜치와 상위 브랜치, 커밋 범위, 승인 대기 항목, 미검증 항목, 다음 단계)은 로컬 전용 인수인계 파일에 남기고 커밋하지 않는다 (D-O23).
- 새 도구, 검사, 문서는 필요성이 확인된 경우에만 추가한다 (NFR-ARCH-04). 하나의 Issue 범위 밖은 수정하지 않는다.
- 작업을 넘기거나 위임할 때는 Issue와 관련 식별자, 기준 브랜치와 커밋, 참조할 문서와 절, 변경 허용·금지 범위, 완료 기준, 검증 방법, 승인 범위, 중단 조건을 함께 전달한다. 결과는 4절의 항목과 완료 기준별 충족 여부, 승인 대기 항목으로 보고한다.
- 개발 도구가 기술적으로 실행할 수 있는 작업과 저장소 소유자가 승인한 작업은 다르다. 도구의 권한 설정은 승인을 대신하지 않으며, AGENTS.md 8절의 작업과 소유자가 승인 대상으로 정한 작업은 승인 범위 안에서만 수행한다. 도구별 권한 설정은 로컬에서 관리한다 (D-O15, D-O23).
- 병렬 작업이 끝나면 실행 증거를 보존한 뒤 그 작업이 만든 자원만 정리한다. 승인되지 않은 자원은 삭제하지 않는다.
- 반복되는 실패는 원인을 기록하고, 규칙 보완이 필요하면 Issue로 제안한다. 공통 규칙은 저장소 소유자의 승인 없이 바꾸지 않는다.
