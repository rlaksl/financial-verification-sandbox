# Git 워크플로

기준일: 2026-11-26

## 1. 흐름

Issue 생성 → Ready → Sprint 배정 → 작업 브랜치 → 구현·테스트 → PR → CI → AI 리뷰 → 리뷰 대응 → 자기 리뷰 → Squash Merge → Issue 종료

## 2. 규칙

| 항목 | 규칙 |
| --- | --- |
| 브랜치 | main + 짧은 작업 브랜치. develop은 두지 않으며 배포 구조와 CD를 설계할 때 필요성을 다시 판단한다 (D-O05) |
| 브랜치 이름 | `type/이슈번호-짧은-설명` |
| 커밋 | `type(scope): 한국어 설명` |
| type | feat, fix, refactor, perf, test, docs, build, ci, chore, poc |
| scope | 모듈 이름, PoC 후보(m1, m2, m3, d, tf), docs, ci 등 |
| PR 제목 | 커밋과 같은 규칙. Squash 후 main의 커밋 제목이 된다 |
| 병합 | Squash Merge만 사용한다. Squash 시 PR 제목이 커밋 제목으로 쓰이도록 저장소 설정을 확인한다 |
| PR 범위 | 하나의 이슈. 보안 영향이 큰 변경은 다른 변경과 섞지 않는다 |
| Workflow 변경 | `.github/workflows` 변경은 단독 PR로 한다 |
| 이슈 연결 | PR 하나로 이슈의 완료 기준을 모두 충족할 때만 `Closes #번호`를 쓰고, 중간 구현 PR은 `Refs #번호`로 연결만 한다 |
| 작성자 표시 | 자동 생성 도구의 공동 작성자 표시나 생성 문구를 커밋·PR에 넣지 않는다. Git 작성자 정보를 임의로 바꾸지 않는다 (D-O14) |
| 커밋·Push·PR | 저장소 소유자의 명시적 요청이 있을 때만 수행한다 |
| 개인 도구 설정 | 저장소에 포함하지 않는다 (D-O15) |

develop을 두지 않는 이유: develop이 해결하는 문제(배포 단위 통합, 통합 환경 분리)가 현재 없다.

## 3. Issue 템플릿

공통 항목:

| 항목 | 내용 |
| --- | --- |
| 목적 | 왜 필요한가 |
| 완료 기준 | 무엇이 확인되면 Done인가 |
| 관련 식별자 | FR, NFR, D, U, T, G, SC |
| 보안 영향 | 있음/없음, 관련 위협 |
| 착수 전 결정 | 필요한 미결정 정책 (Feature) |
| 검증 방법 | 테스트, 시나리오, 측정 |

PoC Gate 템플릿에는 선행 조건, 시나리오 목록, 판정 상태 기록란, 실패 원인 분류란을 추가한다.

## 4. PR 템플릿

| 항목 | 내용 |
| --- | --- |
| 관련 이슈 | `Closes #번호` 또는 `Refs #번호` |
| 변경 요약 | 무엇을, 왜 |
| 보안 영향 | 관련 위협·요구사항 식별자. 영향 없음이면 그 근거 |
| 확장 방식 | E1 ~ E5 중 해당, 교체한 기본 동작과 보존한 검증 |
| 검증 | 실행한 테스트와 시나리오 판정, 실행하지 못한 것 |
| 문서 | 갱신한 결정 대장·쟁점 대장·ADR·API 문서 |
| AI 리뷰 대응 | 반영·미반영·보류 건수와 보류 항목의 후속 이슈. 리뷰를 받지 못했으면 미수행과 사유 |
| 자기 리뷰 | 비밀값·개인정보 미포함, 로그에 민감정보 없음, 테스트 결정성, 실패 경로 테스트 포함, 문서와 코드 일치 |

## 5. Rulesets 설정 순서

| 순서 | 단계 | 확인 |
| --- | --- | --- |
| 1 | 최소 초기 커밋 | — |
| 2 | GitHub Projects 설정 | 필드와 View 동작 |
| 3 | Milestone과 Issue 생성 | Issue Type, Sub-issue 동작 |
| 4 | 작업 브랜치와 첫 PR | 템플릿 동작 |
| 5 | CI 설정 | 실제 실행되는 Job 이름 확인 |
| 6 | Rulesets 활성화 | PR 필수, 승인 수 0, 필수 상태 검사(5에서 확인한 Job), 대화 해결 필수, 강제 Push·삭제 차단, 선형 이력, 우회 목록 비움 |
| 7 | 차단 검증 | 의도적으로 실패하는 PR로 병합이 실제로 막히는지, 해결되지 않은 대화가 있을 때 막히는지 확인 |
| 8 | AI 리뷰 연동 | 이용 자격 확인 후 |
| 9 | 정식 개발 프로세스 시작 | — |

승인 수가 0인 이유: 혼자서는 자기 PR을 승인할 수 없다. 자기 리뷰는 PR 템플릿의 체크리스트로 한다.

## 6. 운영 중 발생할 수 있는 상황

| 상황 | 규칙 |
| --- | --- |
| 필수 Job 이름 변경 | 한 PR에서 바로 바꾸지 않는다. 새 이름의 Job 추가(기존 Job과 함께 실행) → 새 Job 성공 확인 → Rulesets 필수 검사에 새 이름 추가 → 기존 이름을 필수에서 제거 → 기존 Job 삭제 |
| 문서 변경 PR의 필수 검사 누락 | 필수 검사로 지정한 Workflow에는 실행 자체를 건너뛰는 경로 조건을 두지 않는다. 문서 PR에서 무거운 단계를 줄이려면 Job 내부에서 조건 처리한다 |
| 실행 조건으로 인한 Pending | 필수 검사 Workflow가 모든 PR에서 실행되도록 트리거와 브랜치 조건을 확인한다 |
| 신규 검사 등록 | Job 추가 → 실제 PR에서 성공 확인 → 필수 검사 등록 |
| 외부 리뷰 도구 장애 | AI 리뷰는 필수 검사로 등록하지 않는다 |
| Rulesets 설정 오류 | 저장소 관리자가 Rulesets를 수정하거나 일시 비활성화해 복구하고, Chore 이슈에 원인·조치·재활성화를 기록한다. 우회 목록 추가로 해결하지 않는다. 복구 가능 범위는 설정 시 확인한다 |
