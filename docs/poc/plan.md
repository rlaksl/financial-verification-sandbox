# PoC 계획

기준일: 2026-11-26

**현재 상태: 어떤 시나리오도 실행하지 않았다. 모든 시나리오의 판정은 "미실행"이다.**

## 0. 원칙

| 원칙 | 내용 |
| --- | --- |
| 범위 | 업무 기능 전체를 구현하지 않고 기술 선택에 필요한 최소 보안 경로만 검증한다 (D-V02) |
| 통과 조건 | 필수 보안 요구사항은 다른 장점이나 성능으로 상쇄할 수 없다 (D-V04) |
| 실패 해석 | 하나의 구현 방식이 실패했다고 기술 자체가 불가능하다고 결론 내리지 않는다 |
| 채택 | 필수 보안 요구사항을 충족하지 못한 후보는 채택하지 않는다. 증거가 부족하면 채택을 보류한다 |
| 기록 | 실행하지 않은 시나리오를 통과로 기록하지 않는다. 명세·소스 확인은 실행 검증이 아니다 |
| 회귀 | 확장 회귀 테스트와 필수 보안 시나리오는 해당 기능을 처음 구현하는 관문부터 적용한다 (D-V07) |
| 진행 | M 트랙과 D 트랙은 독립적으로 진행하되 테스트 계약, 하네스, 실행 환경, 평가 기준은 공유한다 |

### 1.2 공통 구성 요소

| 구성 요소 | 역할 |
| --- | --- |
| 공통 최소 보호 API | 본문, 쿼리, Idempotency-Key, operationId를 받는 단일 POST 자원. operationId는 고객사별로 유일하다 (업무 불변식). 모든 후보가 같은 계약을 사용한다 |
| 토큰 엔드포인트 | 후보별 인증·바인딩 방식 적용 |
| 공통 시나리오 모듈 | SC 식별자를 가진 시나리오를 후보별로 실행 |
| 테스트 고객사 클라이언트 | Assertion, DPoP Proof, 메시지 서명, 클라이언트 인증서를 생성. 키와 인증서는 테스트 실행 중 생성한다 |
| 변조 프록시 | 요청 변조, 선도착, 지연·차단 재현. TLS 레코드 변조(TLS 보호 구간 내부)와 TLS 종료 후 평문 변조(L7 종료·재암호화, 고객사 측 TLS 검사 장비 재현)를 구분해 수행한다 |
| 최소 등록 정보 검증 | 변조된 등록 정보가 인증 판단에 쓰이지 않는지 확인하는 최소 구현 |
| 시간 주입 | 시계 오차·역행 재현 |
| DB 역할 | W1 시나리오용 최소 역할 분리 |

### 1.3 디렉터리 (계획)

```
poc/
├─ scenarios/      공통 시나리오와 테스트 클라이언트
├─ harness/        변조 프록시, 장애 주입, 측정 도구
├─ m1/ m2/ m3/ d/  후보별 구현
└─ token-format/   토큰 형식 분리 실험
```

정식 서비스 코드(`app/`)는 `poc/`에 의존하지 않는다 (D-O18).

### 5.2 G1-b L4 TLS Passthrough

| 항목 | 내용 |
| --- | --- |
| 선행 조건 | G1-a, L4 프록시 구성 |
| 관련 | A3-b / T-07, T-28 / NFR-SEC-13, NFR-SEC-14 |

| SC | 시나리오 | 기대 결과 |
| --- | --- | --- |
| SC-G1B-01 | Passthrough 경유 요청 | 애플리케이션이 클라이언트 인증서 취득 |
| SC-G1B-02 | 프록시가 서버 키 없이 중간에서 TLS를 다시 맺으려 시도 | 클라이언트 측 핸드셰이크 실패 |
| SC-G1B-03 | 고객 IP 전달 | 선택한 전달 방식으로 확인되고 위조 헤더는 무시 |
| SC-G1B-04 | 프록시가 요청을 지연·차단 | 무결성에는 영향 없음 (가용성 영향만 기록) |
| SC-G1B-05 | (TLS 보호 구간 내부 변조) Passthrough 프록시가 전달 중인 TLS 레코드를 변조. 보호 API와 토큰 엔드포인트 각각 수행 | 연결 종료. 변조된 요청이 애플리케이션에 도달하지 않음 (가용성 영향만 기록) |

**M 계열 요청 무결성의 판정 범위.** mTLS 연결의 성공·거부(SC-G1A-01·02, SC-G1B-02)만으로 요청 무결성 통과를 판정하지 않는다. TLS는 TLS를 맺은 두 지점 사이의 구간만 보호한다. L4 Passthrough에서는 프록시가 암호문만 다루므로 TLS 보호 구간이 애플리케이션까지 이어지고(SC-G1A-09, SC-G1B-05), L7 TLS 종료에서는 프록시 이후 구간과 프록시 자체가 TLS 보호 밖이다(SC-G1A-10). TLS가 보호하지 않는 구간을 보호한다고 주장하지 않는다. 고객사 측 TLS 종료 전 구간은 A3-a 전제 안에서만 다룬다(SC-G1A-11).

| 비교에서 제외 | F3으로 분류되고 근거가 있음 / 해결에 E5가 필요함 / 직접 구현한 보안 코드의 정확성을 시나리오로 증명하지 못함 |
| 추가 검토 | E4가 필요함, 시나리오를 실행할 방법이 없음, 명세 해석이 갈림, F4 |

구현 실패를 기술 자체의 불가능으로 일반화하지 않는 것과, 필수 보안 요구사항을 충족하지 못한 후보를 채택하지 않는 것은 별개의 원칙이다.

### 7.4 정책 의존 시나리오

자체 강화 정책에 따라 기대 결과가 달라지는 시나리오(SC-G4-06 등)는 필수 통과 판정에서 분리하고 정책 결정 후 필수 여부를 확정한다.

### 7.5 종합 판정

판정 단위는 시나리오 → 관문 → 계열 → 요구사항 순으로 올라간다. 상위 단위는 아래 규칙으로만 하위 판정을 모으며, 결과는 검증 상태 값(미검증 / 검증 예정 / 검증 통과 / 검증 실패 / 검증 불충분 / 해당 없음)으로 기록한다.

| 단위 | 판정 대상 |
| --- | --- |
| 시나리오 | 7.1의 판정 상태 |
| 관문 | 해당 관문(V1)의 적용 가능한 필수 시나리오 |
| 계열 | 그 계열에 적용되는 관문, 계열 공통 시나리오(V2), 해당하는 TF 시나리오(V3) |
| 요구사항 | 6절 추적표에서 그 요구사항에 연결된 계열별 시나리오. 계열마다 따로 판정한다 |

| 종합 판정 | 조건 (위에서부터 먼저 적용) |
| --- | --- |
| 검증 실패 | 적용 가능한 필수 시나리오 중 하나 이상이 실패 |
| 검증 불충분 | 실패는 없지만 일부 필수 시나리오만 실행했거나, 실행한 시나리오의 증거가 판정에 부족함 |
| 미검증 또는 검증 예정 | 필수 시나리오를 하나도 실행하지 않음. 선행 조건과 실행 계획이 확정됐으면 검증 예정 |
| 검증 통과 | 적용 가능한 필수 시나리오가 모두 통과이고 증거가 기록됨 |
| 해당 없음 | 적용되지 않는 근거가 기록된 경우에만. 근거 없는 해당 없음은 미실행으로 본다 |

- 해당 없음으로 판정한 시나리오는 상위 단위의 판정 대상에서 빼되 통과로 세지 않는다. 하위가 모두 해당 없음이면 상위도 근거와 함께 해당 없음이다.
- 정책 의존 시나리오(7.4)와 "통과 조건 아님"으로 표시한 상호운용 시나리오는 필수 판정 대상이 아니며 결과만 따로 기록한다.
- 필수 보안 요구사항의 실패는 성능, 운영 편의, 다른 시나리오의 통과로 상쇄하지 않는다. 계열이 검증 실패이면 7.3의 채택 불가이고, 검증 불충분·미검증이면 채택 보류다.
- 실행하지 않은 시나리오를 통과로 집계하지 않는다.

## 8. 확장 방식 기록

구현마다 남긴다: 확장 등급(E1 ~ E5), 사용한 공개 지점(SRC 식별자), 대체한 기본 동작, 보존한 기본 검증, 회귀 테스트 이름.

## 9. 공정한 성능 비교 (Phase 2)

필수 보안 시나리오를 통과한 후보만 최종 성능·운영 비교 대상으로 삼는다. 측정하지 않은 수치는 문서에 쓰지 않는다 (NFR-OPS-04). 측정 전에 우열을 판단하지 않는다.

| 조건 | 내용 |
| --- | --- |
| 실행 환경 | 같은 전용 환경 (공유 CI 러너는 기능 검증용) |
| 소프트웨어 | 같은 JDK·JVM 옵션, 같은 DB·Redis 버전과 설정 |
| 암호 알고리즘 | 이름이 아니라 동등한 보안 강도 기준 (U-32) |
| 통제하거나 별도 측정할 변수 | 토큰 발급 빈도, 토큰 수명, 연결 재사용, 동시 연결 수, 요청 빈도, 저장소 구성, 클라이언트의 서명 생성 비용, 서버의 검증 비용 |
| 절차 | 워밍업, 측정 시간, 반복 횟수, 통계 방법을 측정 전에 고정 |
| 지표 | D-V06 |
